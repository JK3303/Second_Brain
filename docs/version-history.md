## Using versions in shared work

The version records an accepted contribution milestone, not a score for the
contributor or a requirement to match another repository's number. A reviewed
contribution can improve another workspace while the two versions advance
independently. A new component does not automatically constitute a new milestone.

For a useful orientation, ask:

> What does this version help me do, what evidence supports that, and what still
> needs my decision?

### A small handoff across repositories

When work crosses a boundary, carry these four answers in the existing
conversation, PR, or authorized handoff. Include only what the recipient needs;
this is a writing aid, not a new form, tracker, or reporting obligation.

| Answer | What to carry |
| --- | --- |
| Outcome | What useful result is being sought, and for whom? |
| Source | Which authorized record is current? Include its revision or date when available, and identify any superseded record. |
| Decision | What is accepted, what remains open, and who can decide? |
| Next action | What happens next, who has accepted that responsibility, and how will completion be checked? If no one has accepted it, say so. |

Keep source authority in its original home. A link does not grant access; use an
authorized reference the recipient can open, or state the access gap. A public
handoff must omit private client identities and records. A version number is
context, not permission to copy, synchronize, publish, or act in another repository.

### One shared example, viewed from a contribution workspace

Fictional case: an accepted delivery date is June 10, and a new message requests
June 17. The request has not been accepted. Prepare a reviewable change that
preserves the accepted date, labels the requested date as pending, and identifies
the decision needed before an update. Do not treat the new message as approval.

Keep real source evidence in the authorized private workspace. If the useful
contribution is a public template or test, use fictional dates and records; the
PR explains the behavior without copying the client's material. A merged tool
change does not update a business commitment. This example is illustrative,
not evidence that a live trial passed.

Repository versions advance independently of component, runtime, and
workspace-standard versions. This designation preserves their existing values,
provenance, and approval boundaries. It introduces no new runtime behavior,
capture, reporting requirement, permission, or next-increment objectives.
